
================================================================================
  STANDOFF — AI HOSTAGE NEGOTIATION GAME
  BACKEND ARCHITECTURE ABSTRACT
================================================================================

OVERVIEW
--------
Standoff is a real-time, voice-first AI hostage negotiation game. The player
takes on the role of a crisis negotiator (PM, Collector, NIA officer, etc.) and
must resolve a dynamically generated hostage scenario within 15 minutes through
conversation alone. The backend is a multi-agent pipeline built on AutoGen,
powered by a GraphRAG-generated memory system, and orchestrated via a FastAPI
WebSocket server.

================================================================================
PHASE 1: SCENARIO GENERATION (on game start)
================================================================================

STEP 1 — VECTOR RETRIEVAL (PagedIndex / ChromaDB)
  - 100 real-world inspired hostage crisis case abstracts stored in a vector DB.
  - On game start, a random domain seed (location type, criminal archetype,
    motive category) is selected.
  - The vector DB retrieves 2-3 thematically similar reference cases.
  - These are used as style/logic anchors — NOT copied. The LLM invents all
    specifics.
  - Note: RAG here is purely for generation grounding, not retrieval at runtime.

STEP 2 — CASE GENERATION LLM (Qwen3-235B via SambaNova)
  - A single large prompt generates the full scenario JSON:
    {
      "scenario_title": str,
      "location": { type, city, floor_plan_description },
      "player_role": { title, authority_level, resources_available },
      "hostage_taker": {
        "name", "age", "archetype",        -- desperate_parent | ideological | cornered_criminal | revenge_driven
        "backstory", "core_wound",         -- the real reason they're here
        "demands": [ { demand, priority, negotiable } ],
        "breaking_points": [ trigger → emotional_shift ],
        "stress_baseline": 0-100,
        "trust_baseline": 0-100,
        "voice_cues": str                  -- how they speak
      },
      "hostages": [
        { "name", "age", "role", "relationship_to_taker", "health_status" }
      ],
      "intel_layers": [                    -- unlocked progressively by Intel Agent
        { "trigger", "info", "relevance" }
      ],
      "events": [                          -- time/state-triggered events
        { "trigger_type": "time|stress|trust|keyword",
          "trigger_value": any,
          "event": str,
          "effect": { stress_delta, trust_delta, hostage_status_change } }
      ],
      "solution_path": str,                -- hidden narrative of how this resolves best
      "aftermath_seeds": { ... }           -- used by aftermath generator at end
    }

STEP 3 — GRAPHRAG MEMORY GENERATION
  - Same pattern as Interroga. GraphRAGAgent reads the scenario JSON.
  - Generates memory folders for:

    /standoff_agents_{case_id}/
    ├── hostage_taker/
    │   ├── identity.json        -- name, age, archetype, personality traits
    │   ├── knowledge.json       -- what they know: demands, layout, who's watching
    │   ├── beliefs.json         -- what they believe about police, government, system
    │   ├── memories.json        -- what happened today that brought them here
    │   ├── emotional_state.json -- current stress, trust, anger, despair levels
    │   └── breaking_points.json -- what topics/phrases shift their state
    ├── hostages/
    │   └── {name}.json          -- health, relationship to taker, emotional state
    ├── intel_layers/
    │   └── intel.json           -- progressive unlock data
    ├── event_queue/
    │   └── events.json          -- all scheduled/triggered events
    └── player_role/
        └── role.json            -- player's authority, constraints, tone expectations

================================================================================
PHASE 2: RUNTIME GAME ENGINE (during 15-minute session)
================================================================================

SERVER ARCHITECTURE
  - FastAPI WebSocket endpoint: /standoff/ws/{case_id}
  - Single persistent WebSocket connection for the entire 15-minute session.
  - All agent communication is async, event-driven.

AGENT SYSTEM (AutoGen)
  Four agents run in an AutoGen GroupChat with a custom speaker selection
  function. Only one agent speaks per turn — the orchestrator decides who.

  ┌─────────────────────────────────────────────────────┐
  │                  AUTOGEN GROUPCHAT                  │
  │                                                     │
  │  1. HOSTAGE_TAKER_AGENT   (conversational, voice)   │
  │  2. INTEL_AGENT           (event-driven, text)      │
  │  3. COMMANDER_AGENT       (timed, text)             │
  │  4. STATE_MANAGER         (internal, no output)     │
  │                                                     │
  └─────────────────────────────────────────────────────┘

AGENT 1 — HOSTAGE_TAKER_AGENT
  - Active: Always (responds to every player message)
  - Input: Player's voice (transcribed by Sarvam STT) + current emotional state
  - Process:
      • Load system prompt from GraphRAG memory (identity + beliefs + memories)
      • Append current stress/trust levels to prompt dynamically
      • Call Groq (Llama 3.1 / Mixtral) for low-latency response
      • Pass response to Sarvam TTS → audio sent to frontend
  - Output: { response_text, response_audio_b64, stress_delta, trust_delta }
  - State updates after every response:
      • Keyword scanner checks response for breaking_point triggers
      • Stress + Trust meters updated in emotional_state.json

AGENT 2 — INTEL_AGENT
  - Active: Event-driven (fires on: player query, time triggers, state thresholds)
  - Triggers:
      • Player mutes call and types a query → immediate response
      • Time trigger: at T-10:00, T-7:00, T-4:00 → auto-push intel drops
      • State trigger: trust > 60 → unlock deeper personal intel layer
  - Process:
      • Query intel_layers.json for relevant unlocked info
      • LLM formats it as a realistic field officer message
  - Output: { intel_text } → pushed to frontend side panel as text

AGENT 3 — COMMANDER_AGENT
  - Active: Timed (fires every 3-4 minutes regardless of conversation state)
  - Triggers:
      • T-12:00 → "Get him talking. Find out what he really wants."
      • T-8:00  → "We need a hostage released in the next 5 minutes."
      • T-4:00  → "SWAT is ready. Your call — do we breach or do you close this?"
      • Stress > 85 → "He's losing it. Change your approach NOW."
  - Process: Template + LLM to generate realistic commander pressure dialogue
  - Output: { commander_message } → pushed to frontend as alert text

AGENT 4 — STATE_MANAGER (internal orchestrator)
  - Not an LLM agent. Pure Python logic.
  - Runs after every turn:
      • Check event_queue.json for trigger conditions (time, stress, trust, keyword)
      • Fire events: hostage released, hostage hurt, taker escalates, gun fired
      • Update game_state.json: { stress, trust, hostages_alive, time_remaining }
      • Determine if game ends: surrender | walkout | breach | time expired

EVENT ENGINE
  Events are pre-generated in the scenario and stored in event_queue.json.
  The State Manager polls this after every turn.

  Event types:
    TIME_TRIGGER    → fires at specific elapsed time (e.g., T-5:00)
    STATE_TRIGGER   → fires when stress/trust crosses threshold
    KEYWORD_TRIGGER → fires when player says a sensitive word (family, money, etc.)
    HOSTAGE_TRIGGER → fires based on hostage health/behavior

  Event effects:
    → Inject dialogue into Hostage-Taker's next response
    → Push a hostage action to frontend (sound effect / status change)
    → Push intel drop
    → Modify stress/trust directly

VOICE PIPELINE (same as Interroga)
  Player mic → WebSocket → PCM audio bytes
  → Sarvam STT → transcript
  → Keyword scan (event check)
  → Hostage-Taker Agent LLM
  → Sarvam TTS → audio bytes
  → WebSocket → frontend plays audio

================================================================================
PHASE 3: ENDGAME (at T-0:00 or surrender)
================================================================================

SCORING
  Computed from final game_state.json:
    Hostages released alive   : 0-50 pts (proportional)
    Hostage-taker surrendered : 0-25 pts
    No shots fired            : 0-15 pts
    Bonus: intel gathered     : 0-10 pts
    Total: 0-100

AFTERMATH GENERATOR
  - Reads: final game_state, full conversation transcript, scenario aftermath_seeds
  - LLM prompt: "Given this negotiation transcript and outcome, write a
    journalistic 3-paragraph epilogue describing what happened in the days
    following the incident. Reference specific player decisions."
  - Output: A narrative news-report-style aftermath story.
  - This is the shareable moment. Players screenshot this.

================================================================================
TECH STACK
================================================================================

  Case Generation     : Qwen3-235B (SambaNova)
  Runtime LLM         : Groq (Llama 3.1 8B / Mixtral 8x7B) — low latency
  Agent Framework     : AutoGen (GroupChat + custom speaker selection)
  Memory System       : GraphRAG (same as Interroga)
  Vector DB           : ChromaDB (replaces FAISS — persistent, filterable)
  STT                 : Sarvam AI (saarika:v2.5)
  TTS                 : Sarvam AI (bulbul:v3)
  Server              : FastAPI + WebSocket
  Session State       : In-memory dict (Redis if scaling)
  Timer               : Server-side asyncio countdown task per session

================================================================================
KEY DIFFERENCES FROM INTERROGA
================================================================================

  Interroga                      Standoff
  ─────────────────────────────────────────────────────
  REST endpoints (HTTP)          WebSocket (persistent)
  Question limit (20/suspect)    Time limit (15 minutes)
  5 suspects, player chooses     1 hostage-taker, always active
  Task Agent (on demand)         Intel Agent (event-driven + on demand)
  No background events           Full event engine
  Judge scores answer            Score computed from game state
  No aftermath                   Procedural aftermath narrative
